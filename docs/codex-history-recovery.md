## 一、问题原理

“聊天记录消失、只剩项目空文件夹”通常不是单一故障，而是两个层面没有一起恢复。

第一层是聊天历史可见性。Codex 的 SQLite 线程记录、sessions 和 archived_sessions 中的 JSONL 元数据、session_index.jsonl 需要保持一致。如果 model_provider 元数据发生分裂，聊天可能仍然存在，但在侧边栏中不可见。

第二层是项目工作区连续性。聊天记录保存的是项目的绝对路径。只恢复 Codex 运行状态、重新创建同名项目文件夹，并不等于恢复了项目文件本身，因此文件链接可能只能打开空目录。

## 二、受控自我修复的原理

1. **取证：**先只读检查进程、provider、SQLite、JSONL、索引、项目路径和备份。
2. **分类：**判断是工具故障、聊天可见性问题、项目文件缺失，还是数据确实丢失。
3. **保护：**修复前创建针对本次操作的回滚备份，先做 dry-run。
4. **最小修复：**只修改导致问题的最小范围，不删除或重建整个 .codex。
5. **验证：**重新检查数据库、JSONL、样本聊天和真实项目文件，确认后才能声称修复完成。

**重要：**Codex 不能凭空恢复不存在的项目文件。如果原始文件不在本机，必须从可验证的备份恢复；没有备份时应明确报告“文件未找到”，不能伪造修复结果。

## 三、可直接复制给 Codex 的提示词

```text
你现在进入“Codex 受控自我修复模式”。问题现象：聊天记录可能消失，或者恢复后只剩项目空文件夹。请区分：A. Codex 运行时或工具故障；B. provider 元数据不一致导致聊天历史不可见；C. 项目绝对路径存在，但实际项目文件没有恢复；D. 文件和聊天数据确实缺失。严格规则：1. 第一阶段只能只读检查，不得修改、删除、移动或覆盖任何文件。2. 不得删除或重建 .codex、sessions、archived_sessions、state_*.sqlite、session_index.jsonl、登录状态或缓存。3. 不得擅自修改 model_provider 名称；先读取当前 provider，再检查 SQLite 和 JSONL 是否一致。4. 不得把“聊天不可见”直接判断为“聊天已删除”。5. 不得把“项目空文件夹”判断为“项目文件已恢复”。6. 不得由代理重启 Codex。修改配置、写入数据库或恢复文件之前，必须先给出证据、影响范围、回滚方案，并等待我明确确认。7. 不要进行无边界递归扫描，只检查与本问题直接相关的路径。请按以下顺序执行：第一步：只读取证- 检查当前 Codex/Codex.exe 进程、版本和工作目录；- 检查当前 provider 配置；- 检查 state_*.sqlite 中线程数量、归档状态和 model_provider；- 检查 sessions、archived_sessions、session_index.jsonl 中的 provider 元数据；- 检查聊天记录引用的项目绝对路径是否存在；- 检查这些项目目录是否只有空文件夹，还是包含真实文件；- 检查是否存在可用备份和最近快照。第二步：输出诊断表字段必须包括：症状、证据、判断、是否真实丢失、最小修复方案、风险。第三步：停止并等待确认只有在我确认后，才可以：- 创建针对本次修复的回滚备份；- 执行 dry-run；- 进行最小范围修复；- 不重启 Codex，遵守本机运行时限制。第四步：修复后验证必须独立检查：- SQLite 与 JSONL 的 model_provider 是否一致；- archived/unarchived 状态是否一致；- session_index.jsonl 是否仍包含目标记录；- 至少读取一个历史线程验证内容可读；- 项目路径下是否存在真实文件；- 是否产生重复线程、孤儿进程或新的索引错误。最后报告：1. 根因；2. 修复了哪些文件；3. 没有修复哪些内容以及原因；4. 回滚备份位置；5. 验证结果；6. 剩余风险。没有完成验证前，只能说“已执行修复步骤”，不能说“问题已解决”。
```

## 四、如何使用

1. 在受影响设备的新 Codex 任务中粘贴完整提示词。
2. 把“问题现象”替换成同事看到的实际表现，并补充具体项目路径和报错。
3. 先让 Codex 完成只读诊断；看到修复方案后，再明确回复“确认执行修复”。
4. 修复后，要求 Codex 按第四步逐项验证，并保留回滚备份路径。

## 五、修复完成标准

| 检查项 | 完成标准 |
|---|---|
| 聊天历史 | 数据库、JSONL 和 session_index.jsonl 元数据一致，样本线程可读取。 |
| 项目工作区 | 路径下存在真实项目文件，而不只是空文件夹。 |
| 修复安全性 | 有回滚备份，没有删除原始状态，也没有未经确认的重启或写入。 |
| 最终结论 | 明确区分已恢复、未找到和无法验证的部分。 |
